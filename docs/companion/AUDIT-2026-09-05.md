# PixelPals audit — 2026-09-05

Verdict: **not ready for release acceptance or further feature expansion**. The existing passing suite did not cover important integration failures. Production code was not changed during this audit; two regression tests were added to preserve reproducible failures.

Source checkpoint: `ff7e87d` on `feature/pixelpals-living-companion`. The legacy branch remains unchanged. This is a cross-system audit, not a claim that every line, device combination or animation frame has been individually certified.

## Blocking findings

### A1 — A stale status refresh can undo completed care (P1, reproduced)

`PixelPalsRepository.kt:140-150` reads status, reconciles it and writes the entire entity outside a Room transaction. The home, care panel and service can refresh independently while a care transaction commits. A refresh that read old status can overwrite the new needs after feeding completes.

The new `concurrentStatusRefreshDoesNotOverwriteCompletedFeeding` test coordinates the two readers with latches, using an in-memory database and controlled clock. Feeding returned hunger 99; after the older refresh completed, persisted hunger was 69. This is an actual lost update, not a timing-only UI assertion.

Fix direction: serialize read/reconcile/write with care and reward mutations, including initial entity creation and active-minute bond updates. Validate overlapping refresh, care, recovery and expedition departure. Review transaction boundaries before changing only the caller.

### A2 — Consumables are consumed before their local grant (P1, source-confirmed; Play failure injection pending)

`GooglePlayBillingRepository.kt:281-314` calls `consumeSafely`, then `markPlayPurchaseConsumed`, then `grantPlayPurchaseOnce`. There is no durable pending purchase record before consumption. A process death after successful consumption but before the grant leaves no wallet update and no local token record to resume. `markConsumed` is an UPDATE and changes no row on a first purchase because the row is inserted only by the later grant.

This order also exists on the legacy branch; it was not introduced by the companion work. Debug builds instantiate a different billing repository and cannot validate this path.

Fix direction: persist idempotent fulfillment/recovery state before the irreversible consumption step, then retry consumption and acknowledgement safely. Test process loss at each boundary and restore from a Play test track. Do not treat APK signing or local ledger unit tests as proof of real billing recovery.

### A3 — Delayed expedition return triggers hibernation (P1, reproduced)

`CompanionRepository.kt:103-108` shifts illness timestamps and `lastUpdatedAt` but leaves `lastInteractionAt` unchanged. `PetNeedsEngine.hasReachedHibernation` uses the latter. The travelling pet is frozen until the request is claimed, but returning after eight days immediately converts HEALTHY into HIBERNATING.

The new `delayedReturnDoesNotCountTravelAsAbsence` test reproduces this using a selected, enabled Corgi and an eight-day controlled clock advance. Review all care timestamps and both cancellation and successful return; do not fix this by granting unrelated care or resetting progress.

## Functional and presentation gaps

### A4 — Room movement does not respect object depth or facing (P2, source-confirmed)

`HomeSceneView.kt:79-85,144-158` supplies only target X to the motion controller and always draws the actor on baseline 650. Beds/toys can occupy three rows, so moving a bed to a rear row does not move the resting actor to that bed. `CompanionMotion.isFacingLeft` is calculated but never used by the renderer. Approaches use PET care frames rather than species locomotion. Continuous X movement alone does not meet the agreed contact, turning and anatomy standard.

### A5 — Error retry does not restart failed world/journal observation (P2, source-confirmed)

`CompanionViewModel.kt:38-48` catches upstream database errors by setting a Boolean and completing the flow. `refresh()` only reloads selection/snapshots; setting the same selected pet does not restart a completed upstream collection. The home retry button can clear the message while leaving home/inventory/journal updates stale. Add an explicit retry trigger or resilient upstream collection and an injected transient-failure test.

### A6 — Personality and memories are only partially implemented (plan gap)

Learned play/touch counts adjust home speed; `feedCount` and profile curiosity do not currently affect behavior. A favorite is set manually by `chooseObject`; interactions do not learn an object preference. The service observes the home to configure the desktop object, but does not pass this learned personality into desktop behavior. The journal renderer creates text views and dates, not illustrated adoption/care/bond events. Destination cards provide scenery and text rather than distinct illustrated encounters. These must remain explicitly incomplete in the plan.

### A7 — Treasure display depends on device emoji coverage (P2, visually reproduced)

`HomeScenePainter.kt:152` uses raw `Canvas.drawText(treasure, ...)` without a glyph fallback or bundled treasure artwork. The Android 8 emulator displayed a missing-glyph rectangle on the shelf. The home visibility test compares pet pixels and cannot catch this. Use compatible artwork or verify/fallback per treasure.
